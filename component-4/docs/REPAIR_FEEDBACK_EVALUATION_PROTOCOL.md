## 1. Executive Summary & Research Objectives

In the INTELISE architecture, Component 4 verifies generated code submissions and produces machine-readable feedback for Component 3's iterative repair loop when verification fails.

The objective of the future Phase 3C.3 repair-effectiveness evaluation is to rigorously evaluate whether:
1. Machine-readable feedback generated by **LLM-assisted Component 4** (Qwen2.5-Coder 3B) leads to higher downstream patch acceptance rates and fewer repair iterations compared to **deterministic-only Component 4 feedback** or standard **Conventional CI failure traces**.
2. Explainability and localization metrics correlate with downstream repair success without hallucination.

> [!IMPORTANT]
> **Scientific Integrity Notice**:
> Under Phase 3C.2 constraints, no repair outcomes, LLM usefulness ratings, or human evaluations are fabricated. LLM-assisted repair superiority is a research hypothesis to be empirically tested in Phase 3C.3, not an assumed fact.

## 2. Experimental Design & Independent Variables

The experiment will evaluate three distinct feedback conditions provided to the standardized repair agent (Mocked Component 3):

| Condition ID | Feedback Generator | Payload Contents |
| :--- | :--- | :--- |
| **COND-A (Baseline CI)** | Standard Pytest Runner | Raw stdout/stderr, stack trace, failing test assertion. |
| **COND-B (Deterministic C4)** | Multi-Agent Deterministic Verifier | Structured JSON: defect category, deterministic AST line, rule violation, exact failure trace. |
| **COND-C (LLM-Assisted C4)** | Qwen2.5-Coder 3B + Reconciliation | Reconciled JSON: defect category, prioritized line numbers, synthesized diagnostic context, and XAI remediation hints. |

All three conditions will be tested on the exact same set of defective scenarios using identical downstream patch generation budgets and acceptance criteria.

---

## 3. Repair Task Selection

1. **Partition Boundaries**:
   - Repair tasks will be selected strictly from the **Development partition** (`FAM-01` through `FAM-05`) and **Validation partition** (`FAM-06`, `FAM-07`).
   - The **Frozen Held-Out partition** (`FAM-08` through `FAM-10`) is sealed and will be evaluated only once during the final benchmark run, with zero iterative feedback tuning.
2. **Defect Representation**:
   - The repair experiment sample will comprise 50 stratified defective scenarios covering all 7 defect categories:
     - Functional bugs (15)
     - Security vulnerabilities (10)
     - Performance bottlenecks (5)
     - Regressions (5)
     - Integration defects (5)
     - Semantic drift (5)
     - Non-convergent defects (5, to test multi-iteration cycle detection)
3. **Control Inclusion**:
   - 10 clean controls will be included blindly to verify that the repair agent does not attempt to "repair" non-defective code when Component 4 reports `PASSED`.

---

## 4. Standardized Repair Generation Procedure

To prevent prompt bias or confounding model capability:
1. **Model Identity**: The downstream repair generator (Component 3 simulator) will use a fixed prompt template and a fixed temperature ($T=0.2$) with seed $42$.
2. **Standardized Context**:
   The repair agent receives:
   - Target source code under test (`module_code`).
   - The feedback payload corresponding to Condition A, B, or C.
   - Requirements specification (`REQ-001`).
3. **Iteration Budget**:
   - Maximum iterations per scenario: $K = 3$.
   - At each iteration $k \in \{1, 2, 3\}$, the repair agent produces a candidate patch $P_k$.
   - Component 4 re-verifies $P_k$ and provides iterative feedback if verification fails again.

---

## 5. Independent Acceptance Oracles & Regression Checks

A candidate patch $P_k$ is accepted as a genuine repair **if and only if** it satisfies all three independent criteria:

1. **Independent Oracle Pass**:
   - $P_k$ must pass the independent ground-truth verification oracle (`oracle_code`).
   - The independent oracle is executed outside Component 4 and outside the repair agent.
2. **Regression Invariant Pass**:
   - $P_k$ must pass all baseline test cases that passed on the clean implementation.
   - No new runtime exceptions, syntax errors, or degraded outputs may be introduced.
3. **Semantic Integrity Check**:
   - The repaired module must satisfy the original behavioral contract without trivially deleting assertions or bypassing security guards.

---

## 6. Repair Success Criteria & Quantitative Metrics

| Metric | Definition | Formula / Measurement |
| :--- | :--- | :--- |
| **Pass@1** | Proportion of scenarios repaired on the first attempt ($k=1$). | $\frac{\sum [k_{\text{success}} = 1]}{N}$ |
| **Pass@3** | Proportion of scenarios repaired within 3 attempts ($k \le 3$). | $\frac{\sum [k_{\text{success}} \le 3]}{N}$ |
| **Iteration Efficiency** | Mean number of iterations required to achieve accepted repair. | $\frac{1}{N_{\text{success}}} \sum k_{\text{success}}$ |
| **Regression Rate** | Rate at which candidate patches break previously passing tests. | $\frac{N_{\text{regressed}}}{N_{\text{attempts}}}$ |
| **Non-Convergence Detection** | Accuracy of detecting oscillating or cyclic repair loops. | $F_1$ score on `non_convergent_by_design` category. |

---

## 7. Failure, Timeout, and Sandbox Handling

1. **Timeout Policy**:
   - Candidate patch generation timeout: 60 seconds per attempt.
   - Patch execution and verification timeout: 5 seconds per attempt.
   - Scenarios exceeding timeout are logged as `TIMEOUT_EXCEEDED` and marked as failed repairs.
2. **Sandbox Isolation**:
   - All candidate patches are executed inside isolated in-process sandboxes or Docker containers.
   - No filesystem persistence or network access is permitted during repair evaluation.

---

## 8. Candidate Patch Provenance & Auditability

Every candidate patch generated during Phase 3C.3 will be recorded in a tamper-evident audit store:
- `scenario_id`
- `condition_id` (`COND-A`, `COND-B`, or `COND-C`)
- `iteration_index` ($k \in \{1, 2, 3\}$)
- `candidate_patch_sha256`
- `unified_diff`
- `verification_verdict` (`PASSED`, `FAILED`, `REGRESSED`, `TIMEOUT`)
- `wall_clock_duration_ms`
- `token_usage` (prompt tokens, completion tokens)

---

## 9. Blinded Human Evaluation Protocol

In addition to automated acceptance testing, a randomized double-blind human evaluation will be conducted on a subset of 30 feedback artifacts:
1. **Evaluators**: 3 independent software engineers not involved in developing Component 4.
2. **Blinding**: All condition identifiers (`COND-A`, `COND-B`, `COND-C`), model names, and system logs will be stripped. Scenarios and feedback payloads will be presented in randomized order.
3. **Evaluation Criteria (1 to 5 Likert Scale)**:
   - **C1: Actionability** (Can an engineer immediately fix the bug from this feedback?)
   - **C2: Specificity** (Does it pinpoint the precise erroneous operation or boundary?)
   - **C3: Diagnostic Clarity** (Is the explanation lucid, coherent, and correct?)
   - **C4: Localization Accuracy** (Does the indicated location match the root cause?)
   - **C5: Non-Hallucination** (Is the feedback completely free of fabricated APIs or false claims?)
4. **Inter-Rater Reliability**: Fleiss' Kappa ($\kappa$) will be calculated to ensure statistical validity.
