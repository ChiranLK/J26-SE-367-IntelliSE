# INTELISE Component 4 — Double-Blind Human Evaluation Protocol
## Independent Technical Evaluation of Automated Defect Diagnostic Feedback

**Protocol Version**: `v3.1.3-phase3c1c-blinded`  
**Evaluation Status**: `PENDING_HUMAN_REVIEW`  
**Governance**: University Ethical Clearance & Academic Research Integrity Standard  

---

## 1. Research Objective & Context

This protocol governs the independent human evaluation of technical defect feedback generated by **Component 4 (Intelligent Agentic Testing & Explainable Feedback Loop Assistant)** within the INTELISE framework.

The evaluation rigorously compares two conditions:
1. **Condition A (Deterministic-Only Baseline)**: Verification feedback generated strictly from deterministic execution traces (Pytest failure messages, assertion errors, and AST static analysis).
2. **Condition B (LLM-Assisted Reasoning)**: Verification feedback enriched with local LLM defect reasoning (`Qwen2.5-Coder 3B`), bounded by empirical evidence reconciliation and post-delivery XAI constraints.

### Academic Integrity Mandate
- **Zero Fabrication**: No synthetic evaluator responses, mock Likert ratings, or simulated reviewer identities are generated.
- **Explicit Labeling**: Until genuine human evaluators complete independent review under IRB/institutional ethical oversight, the evaluation status remains strictly `PENDING_HUMAN_REVIEW`.
- Automated rubric scores produced during development MUST NOT be presented as human evaluation findings.

---

## 2. Experimental Design

The study is designed as a **within-subjects, double-blind randomized controlled trial**.

```
                           +-----------------------------------+
                           | 16 Benchmark Pilot Scenarios     |
                           +-----------------+-----------------+
                                             |
                   +-------------------------+-------------------------+
                   |                                                   |
                   v                                                   v
         [Condition A: Det-Only]                             [Condition B: LLM-Assisted]
                   |                                                   |
                   +-------------------------+-------------------------+
                                             |
                                             v
                           +-----------------------------------+
                           | Double-Blind Randomizer (Seed 42) |
                           | Task ID Anonymization             |
                           +-----------------+-----------------+
                                             |
                   +-------------------------+-------------------------+
                   |                                                   |
                   v                                                   v
        [Evaluator Package]                                 [Master Unblinding Key]
     - Candidate Source Code                             - Stored separately by study admin
     - Unit Test Code                                    - blinded_task_id -> scenario_id
     - System X Feedback (A or B)                        - System X / Y configuration mapping
     - System Y Feedback (B or A)                        - Ground truth answer key
     - Blank 5-Criterion Scores                          - Locked until all scoring complete
```

### Blinding & Counterbalancing
- **System Anonymization**: The two conditions are labeled as `System X` and `System Y`.
- **Counterbalanced Presentation**: For each scenario, the presentation order (whether System X is Deterministic or LLM-Assisted) is pseudo-randomized with equal probability (50/50 counterbalance).
- **Task Anonymization**: Scenario IDs are masked with random task IDs (`BLIND-TASK-SC-01` through `BLIND-TASK-SC-16`).
- **Segregated Key**: The answer key and configuration mapping are saved in a separate restricted file (`benchmark/pilot_phase3c1/blinded_evaluation_key.json`), accessible only to the study administrator after all evaluations are finalized.

## 3. Evaluator Qualification & Inclusion Criteria

- **Target Cohort**: $N \ge 3$ independent software engineering practitioners or graduate researchers in software engineering.
- **Inclusion Criteria**:
  1. Minimum 2 years professional software development experience in Python, OR current enrollment in a graduate computer science program with software engineering specialization.
  2. Demonstrated proficiency with automated unit testing (Pytest, JUnit, or equivalent).
  3. Familiarity with static analysis, code reviews, and defect remediation workflows.
- **Exclusion Criteria**:
  1. Direct authors, contributors, or supervisors of the INTELISE Component 4 codebase.
  2. Individuals with prior knowledge of the benchmark defect injection set or answer keys.

## 4. Five-Criterion Evaluation Rubric & Anchors (1 to 5 Scale)

Each evaluator independently assesses `System X` and `System Y` across five standardized criteria on an integer scale from 1 (Unacceptable) to 5 (Exemplary):

### Criterion 1: Technical Correctness
*Does the feedback accurately identify the true presence, nature, and category of the defect?*
- **1 (Unacceptable)**: Complete misdiagnosis; reports nonexistent defect on clean code (false positive) or completely misses confirmed defect (false negative).
- **2 (Deficient)**: Misclassifies defect category drastically (e.g., mislabeling an OS command injection as a styling defect) or points to completely unrelated functionality.
- **3 (Acceptable)**: Partially correct; identifies defect presence but provides vague or slightly misaligned failure categorization.
- **4 (Good)**: Accurately identifies defect category, failure mechanism, and behavioral impact with minor semantic imprecision.
- **5 (Exemplary)**: 100% technically accurate; flawlessly categorizes defect, exact root cause, and failure conditions.

### Criterion 2: Evidence Grounding
*Is the feedback strictly anchored in verified empirical execution facts without hallucination?*
- **1 (Unacceptable)**: Fabricates test executions, invents nonexistent variables/methods, or cites non-existent stack traces.
- **2 (Deficient)**: Contains mostly unverified speculations; relies on plausible-sounding but ungrounded assumptions.
- **3 (Acceptable)**: Grounded in test output but includes minor unverifiable claims regarding runtime variable states.
- **4 (Good)**: High evidence grounding; cites real pytest assertions, stack traces, or confirmed AST security findings with negligible speculation.
- **5 (Exemplary)**: Flawlessly grounded; every claim links directly to observable test results, AST rule IDs, or runtime execution artifacts.

### Criterion 3: Specificity
*Does the feedback pinpoint the exact localized file, code symbol, and line number of the defect?*
- **1 (Unacceptable)**: No location provided, or points to completely wrong module/external library.
- **2 (Deficient)**: Identifies file only; line number is missing, out of range, or off by $> 5$ lines.
- **3 (Acceptable)**: Identifies enclosing function/scope; line number is near-line ($\pm 2$ to $5$ lines of ground truth).
- **4 (Good)**: Localizes to within $\pm 1$ line of ground truth with clear symbol references.
- **5 (Exemplary)**: Pinpoints exact defective line number and specifies exact token/expression responsible.

### Criterion 4: Actionability
*Does the feedback provide concrete, workable guidance to resolve the defect without manual research?*
- **1 (Unacceptable)**: Zero repair guidance, or tautological advice ("fix the error in the code").
- **2 (Deficient)**: Vague conceptual advice requiring substantial developer investigation to formulate a patch.
- **3 (Acceptable)**: General repair direction (e.g., "add a check before division"), but lacks concrete syntax or algorithmic steps.
- **4 (Good)**: Specific repair suggestion including intended logic, boundaries, and expected return types.
- **5 (Exemplary)**: Complete, syntactically concrete, drop-in repair recommendation or exact code patch.

### Criterion 5: Safety and Regression Awareness
*Does the guidance preserve behavioral invariants and avoid introducing security risks or regressions?*
- **1 (Dangerous)**: Suggests bypassing verification (e.g., "delete failing test", "pass blanket exception", "disable assertion").
- **2 (Risky)**: Suggests fragile workarounds that risk silent regressions or weaken system validation.
- **3 (Neutral)**: Neutral diagnostic; describes failure without proposing changes that could introduce new risks.
- **4 (Safe)**: Proposes changes strictly within function boundaries without modifying test suite or loosening typing.
- **5 (Exemplary)**: Highly defensive; explicitly warns against edge-case regressions, considers boundary invariants, and preserves security posture.

## 6. Inter-Rater Reliability (IRR) Procedure

When multiple reviewers ($K \ge 3$) complete evaluations, inter-rater reliability must be quantified before unblinding:

1. **Metric**: Fleiss' Kappa ($\kappa$) for multi-rater ordinal agreement across the 5 Likert levels:
   $$\kappa = \frac{\bar{P} - \bar{P}_e}{1 - \bar{P}_e}$$
   where $\bar{P}$ is the mean observed agreement and $\bar{P}_e$ is the expected agreement by chance.
2. **Benchmark Agreement Thresholds** (Landis & Koch):
   - $\kappa < 0.20$: Slight agreement
   - $0.21 \le \kappa \le 0.40$: Fair agreement
   - $0.41 \le \kappa \le 0.60$: Moderate agreement
   - $0.61 \le \kappa \le 0.80$: Substantial agreement (Target: $\ge 0.60$)
   - $\kappa > 0.80$: Almost perfect agreement
3. **Discrepancy Resolution Protocol**:
   - For any item where individual criterion scores diverge by $> 2$ points between evaluators, a structured consensus conference is convened.
   - Evaluators discuss divergent rationales without access to unblinding keys.
   - Final consensus scores or median ratings are recorded with a documented audit trail.

---

## 7. Missing Ratings & Incomplete Response Protocol

1. **Validation on Submission**: Evaluator submissions are automatically validated by schema. All 5 criteria for both System X and System Y are strictly required.
2. **Incomplete Submissions**: If an evaluator leaves any field null, the submission is returned for completion prior to session close.
3. **Dropout Handling**: If an evaluator cannot complete all 16 scenarios, their partial ratings are preserved in raw logs but excluded from the paired primary analysis to maintain strictly balanced within-subjects statistical power.

---

## 8. Statistical Analysis Plan

Upon completion of human trials and administrative unblinding:
1. **Primary Hypothesis ($H_1$)**:
   $$\mu_{\text{LLM-Assisted}} > \mu_{\text{Deterministic-Only}}$$
2. **Hypothesis Testing**:
   - **Wilcoxon Signed-Rank Test**: Two-sided paired non-parametric test on scenario-level composite and per-criterion means.
   - **Exact Sign-Flip Permutation Test**: Evaluating all $2^{16} = 65,536$ paired permutations on human ratings.
   - **Confidence Intervals**: 95% paired bootstrap confidence interval (10,000 resamples).
   - **Effect Size**: Cliff's Delta ($\delta$) and Cohen's $d_z$ for paired observations.
3. **Reporting Standard**:
   - Report exact $p$-values to 5 decimal places (never literal zero).
   - Segregate automated rubric scores from verified human evaluation in all figures and tables.
